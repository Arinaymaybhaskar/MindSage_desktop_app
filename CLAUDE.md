## Commands

```bash
npm run dev            # Vite dev server + Electron (vite-plugin-electron sets VITE_DEV_SERVER_URL). Normal way to run the app.
npm run build          # vite build && electron-builder → installers in release/
npm run release        # same, with --publish always (used by .github/workflows/release.yml on v* tags)
npm run rebuild        # electron-rebuild -f -w better-sqlite3
npm run postinstall    # runs rebuild automatically; without it better-sqlite3 fails to load at runtime
npm test               # vitest run (pure modules + renderer; needs no native build)
npm run test:db        # *.db.test.js under Electron-as-Node: real SQLite migrations, journal CRUD, backup, the AI worker thread
npm run test:e2e       # builds, then launches the real app (Playwright): sign up, write, wait for AI, search. Needs Ollama; E2E_SKIP_AI=1 skips those steps
npm run test:watch     # vitest
npm run typecheck      # tsc -p tsconfig.app.json --noEmit  (renderer only)
npm run lint           # eslint .
npm run format         # prettier --write .    (format:check for CI-style verification)
npm run bench          # SQLite/media/size benchmark suite → docs/benchmarks/results/
npm run bench:ipc      # IPC-boundary benchmark; needs the running app
npm run bench:quick    # db stage, ~25s; the pre-commit hook runs it when runtime code is staged
npm run bench:phase -- <n>   # full suite after Jira release P<n>; needs Ollama, builds first
```

**Benchmarks come in two kinds, kept apart everywhere** (file location, `kind` field, website): a **quick** run on every commit that stages runtime code, from the pre-commit hook, never committed and never blocking; and a **full** run at the end of every roadmap phase (a Jira release, P1, P2, ...), committed. Finishing a phase is not done until `npm run bench:phase -- <n>` has run and its results are committed with a run-index row. See [docs/benchmarks/README.md](docs/benchmarks/README.md#two-kinds-of-run).

Targeted runs: `npm run bench -- --label after-<change>` then `npm run bench -- --compare baseline --label after-<change>`. [docs/benchmarks/BASELINE.md](docs/benchmarks/BASELINE.md) is **generated — never hand-edit it**; [FINDINGS.md](docs/benchmarks/FINDINGS.md) is the hand-written reading, and it **corrects PERFORMANCE.md in two places**. Trust the measurements over the audit prose.

**Running a subset of tests:**

```bash
npx vitest run src/utils/DateFormatter.test.ts   # one file
npx vitest run -t "formats a relative date"       # one test by name
```

**Typecheck, lint and format are all clean; keep them that way.** As of 2026-08-28 `npm run typecheck`, `npm run lint` and `npm run format:check` all report **zero** problems, and tests are green (5 files, 35 tests). This replaces a long-standing baseline of 131 typecheck errors and 106 lint problems, cleared wholesale in a single pass. **A non-zero typecheck or lint exit now means you broke something**, so treat it as a real failure rather than comparing counts against a tolerated baseline.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) **blocks on all four**: typecheck, lint, `format:check` and `npm test`. The `continue-on-error: true` that made the first two report-only is gone, so a red `Typecheck & Lint` check now means what its name says. The pre-commit hook catches the same problems earlier (see **Other tooling** below), but it can be bypassed with `--no-verify`; CI cannot.

Three things that clean-up established, so treat them as conventions rather than incidental style:

- **The IPC bridge is typed, not `any`.** [src/electron.d.ts](src/electron.d.ts) now describes the whole `preload.js` surface, and `window.electron.ipcRenderer.invoke` is generic with an `unknown` default. Callers state the shape they expect, usually through the declared return type of the `src/api/*Service` wrapper that owns the channel. When you add a channel, type its wrapper against what the handler in `electron/methods/*` actually returns; when you add a member to the bridge, add it here too.
- **Context hooks live in `src/hooks/`, not beside the provider.** `useAuth`, `useToast` and `useColorThemeContext` each sit in their own file so the context modules export only components, which is what React Fast Refresh needs and what `react-refresh/only-export-components` enforces. Adding a hook back into a `src/context/*.tsx` file will fail lint.
- **Row shapes live in `src/types/`.** `User.ts`, `Goals.ts`, `Dashboard.ts`, `Ollama.ts`, `Search.ts` and `sqlite.ts` mirror the DDL in [electron/db/connection.js](electron/db/connection.js). SQLite has no boolean, so 0/1 columns are typed `SqliteBoolean`; prefer extending these over redeclaring a near-copy in a component.

**Database tests are a second project.** better-sqlite3 is built for Electron's ABI, so anything that touches the real database is a `*.db.test.js` file, excluded from `npm test` and run by `npm run test:db` under `ELECTRON_RUN_AS_NODE=1` ([vitest.db.config.ts](vitest.db.config.ts), [scripts/run-db-tests.mjs](scripts/run-db-tests.mjs); it needs the `electron-rebuild` build from `postinstall`). They use `electron/db/dbTestUtils.js` and choose their folder through `MS_DB_DIR` / `MS_USER_DATA_DIR` before the first import, because `connection.js` opens the database as a side effect. `searchIndex.db.test.js` and `services/indexer.db.test.js` run the real sqlite-vec extension and the indexer loop with a fake embedding function (no Ollama needed). A new migration needs a case in `migrations.db.test.js`. The end-to-end run is `scripts/e2e/run.mjs`; it waits on the app's own events, never a sleep.

**Test conventions:** tests sit next to the module they cover (`electron/methods/jsonStream.test.js`, `src/api/journalService.test.ts`). [vitest.config.ts](vitest.config.ts) is deliberately separate from [vite.config.ts](vite.config.ts) so `vite-plugin-electron` doesn't boot during tests; it uses jsdom, `globals: true`, `src/test/setup.ts`, and `pool: "threads"` (the default `forks` pool hangs on newer Node). `electron/**` is in the include list, but only **pure modules** are testable there — anything importing `better-sqlite3` or `electron` won't load. `electron/methods/` is no longer copied into the package at all, so the explicit test exclusion that used to sit in the `viteStaticCopy` targets is gone with it.

**Other tooling:** husky's [pre-commit hook](.husky/pre-commit) does two things. First `gitleaks protect --staged` (warns and passes through if gitleaks isn't installed — install it for real protection; allowlist false positives in `.gitleaks.toml`). Then `lint-staged`, which runs `prettier --write` on staged files and `eslint --fix --max-warnings=0` on staged `.ts`/`.tsx`, re-staging whatever it fixes. A commit that would introduce a lint error or a warning is refused. ESLint's flat config ([eslint.config.js](eslint.config.js)) matches only `**/*.{ts,tsx}`, which is why the `lint-staged` globs in `package.json` send `.js`/`.mjs` to Prettier alone; adding them to the ESLint glob makes it fail with "no matching configuration". **That means the whole main process is formatted but never linted** — `electron/**` and `scripts/**` are plain `.js`/`.mjs`, so `npm run lint` says nothing about them. Widening the config is a real (unclaimed) improvement, not a one-line glob change: those files would report fresh errors on their first run. Prettier (`.prettierrc`: LF, double quotes, semicolons, trailing commas, 80 columns) was applied across the repo in one sweep after years of drift, so `format:check` passes; `.prettierignore` excludes all `*.md`, which is why this file is exempt, and also skips `public/rive/` (a vendored webpack bundle) and `docs/benchmarks/results/` (regenerated by every `npm run bench`). [.gitattributes](.gitattributes) pins the working tree to LF on every platform, without which `format:check` would pass on the Linux runner and fail on a fresh Windows clone. `.npmrc` sets `engine-strict=true` against the Node 20–24 range in `package.json`; `.nvmrc` pins 20.

## Branching and workflow

**Branch flow: ticket branch → phase branch → `dev` → `main`.** `dev` is the beta branch, cut from `main`: every finished phase lands in it through one PR, beta testers run builds of `dev`, and only when they are satisfied does `dev` land in `main` through one PR. `main` therefore only ever holds what beta testers have seen. Merge `main` into `dev` (never rebase it) whenever `main` moves.

`main` is protected on GitHub: no direct pushes (enforced for admins too), no force-pushes, no deletions, and merging requires the `Typecheck & Lint` check to pass, which now genuinely means typecheck, lint **and** `npm test` all passing (see above). All work happens on a branch off `main` and lands via PR.

### Naming: branches, commits and pull requests

Work is tracked in Jira, project **KAN** (MindSage) at arinaymaybhaskar7500.atlassian.net. Every branch, commit and PR that does a ticket names its key, so the work and the ticket find each other. One ticket per branch and per PR.

**Branches:** `<type>/<KEY>-<slug>`, for example `fix/KAN-58-ipc-survives-qdrant` or `feat/KAN-52-trash`.

- `<type>` is the conventional-commit type of the main change: `feat` (user-visible behaviour), `fix` (a bug), `perf`, `refactor`, `test`, `build` (packaging, electron-builder, Vite), `ci`, `chore`, `docs`.
- `<KEY>` is the Jira key in capitals. Work with no ticket drops it: `docs/naming-conventions`. Anything bigger than a typo should get a ticket first.
- `<slug>` is two to five lowercase words joined by hyphens, from the ticket summary.
- Delete both the local and remote branch immediately after merge; don't let merged branches accumulate.
- `phase/p<n>-<slug>` — one per roadmap phase (the Jira release), for example `phase/p1-make-the-promise-true`, cut from `dev` when the phase starts. Ticket branches for that phase branch from it and merge back into it, never straight into `dev` or `main`. When the phase's gate passes (every ticket in Ready for release and the owner's own test done, see **The testing loop**) and `npm run bench:phase -- <n>` is committed, the phase branch lands in `dev` through one PR. Merge `dev` into an open phase branch (never rebase it) whenever `main` moves. CI runs on every pull request whatever its base, but not on direct pushes to a phase branch, so run typecheck, lint, `format:check` and `npm test` before merging into one by hand.
- `backup/<slug>` — a snapshot taken before a history rewrite or other destructive git operation (e.g. `backup/pre-coauthor-removal`, taken before stripping `Co-Authored-By` trailers from history). Kept indefinitely as cheap insurance.
- `archive/<slug>` — work deliberately abandoned but kept for reference (e.g. `archive/redesign-preview`, a scrapped redesign). Not meant to merge.
- `claude/<slug>` — branches Claude Code creates on its own in cloud sessions. Rename to the pattern above before opening a PR for ticket work.

### The testing loop (Jira statuses)

A ticket that is built and merged into its phase branch goes to **Ready for testing**, never straight to Done. Done means verified by a person and merged to `main`. From there:

1. **Test.** A *separate* testing agent (never the one that wrote the code, and given only the ticket and its QA-steps comment) launches the real app (`xvfb-run` and Playwright, `MS_REMOTE_DEBUG` or the dev app for debug mode; `scripts/e2e/run.mjs` is the pattern) and works through the ticket's acceptance criteria and QA steps in the UI, thoroughly, including the edge cases the ticket lists. It cannot pass what the sandbox cannot do (no real Ollama, no Windows or macOS packaged build): those parts are reported as not tested, and a ticket labelled `needs-hardware` stays in Ready for testing with the parts that could run recorded in a comment.
2. **Pass.** Everything that can be checked passed: move the story to **Ready for release** and comment exactly what was run and seen.
3. **Fail.** Move the story to **Failed Testing** and file a Jira **Bug** under the same epic with the repro steps, evidence (screenshot, log lines) and what was expected, labelled `release-pN`, `found-in-phase-N` and `phase-N-closeout`, with the phase's release as fix version and linked to the story.
4. **Fix.** The coding agent reads the bug, fixes it on a branch named for the bug (`fix/KAN-nnn-slug`), merges it into the phase branch, and moves **both the bug and the story back to Ready for testing**, with a comment saying what changed and what to retest.
5. **Retest.** The testing agent tests the bug and the story again and sets each status accordingly. Repeat 3 to 5 until every ticket of the phase is in Ready for release.
6. **Owner pass.** The coding agent writes, per ticket, what to test and how (the QA-steps comment, kept current, with what is automated and what is not). The owner tests from those instructions. Only then does the phase branch go to `dev` (and later `dev` to `main`, after the beta testers).

Rules that keep the loop honest: a tester reports what it saw, not what the code intends; a pass never rests on unit tests alone; a bug found in a ticket's own acceptance criteria is the ticket's (it goes to Failed Testing), a bug found elsewhere is filed separately and the ticket may still pass; statuses are changed only by the agent whose step it is.

**Bugs found along the way:** when ticket work, a review or a benchmark turns up a bug that is not the ticket's own, do not widen the ticket. File a Jira **Bug** in project KAN under the closest epic, labelled `found-in-phase-<n>` and `phase-<n>-closeout`, with the phase's release as its fix version, a description saying where it was found and whether it was reproduced or only read from the code, and acceptance criteria. Say so in the PR. Closing a phase includes fixing everything labelled `phase-<n>-closeout` (or deliberately moving it to a later release) before the phase branch goes to `main`.

**Functionality first, design later:** a screen's work is split into two tickets. The functionality ticket (behaviour, data, accessibility, tests) is built and verified first. Its look goes in a separate `design-only` Task under the same epic, in the release that brings the new visual system (labels `design-only`, `ui`; today P3), linked from a comment on the functionality ticket. Do not widen the functionality ticket with colours, fonts or layout polish; do not change behaviour in a design ticket.

**Commits:** [Conventional Commits](https://www.conventionalcommits.org/), as the history already uses: `type(scope): summary`.

- `scope` is the area touched, matching the existing history: `startup`, `db`, `auth`, `journal`, `goals`, `search`, `ai`, `chat`, `people`, `media`, `portability`, `settings`, `updater`, `ui`, `bench`. Leave it out when a change spans the app.
- The summary is imperative, lower case, no full stop, under about 72 characters: `fix(startup): keep IPC working when Qdrant fails to start`.
- The body says why, and what was checked. The last line before any trailers is `Refs: KAN-58`; the Jira GitHub integration links commits by that key.
- A breaking change to stored data or IPC gets `!` after the scope (`feat(db)!: …`) and a `BREAKING CHANGE:` line saying what an existing install goes through.

**Pull requests:** a ticket PR targets its phase branch, not `main`. Title `KAN-58: <ticket summary>`, for example `KAN-58: IPC survives a Qdrant failure`. The body links the ticket, copies its acceptance criteria as a checklist ticked against what was verified, and lists anything left for a follow-up ticket. A ticket labelled `opus-review` in Jira (journal data, migrations, security, the AI pipeline) is reviewed with Opus before merge.

## Architecture

Electron + React + TypeScript desktop journaling app, **offline-first**: data lives in a local `better-sqlite3` DB, Ollama (generation/embeddings) and Whisper.cpp (speech-to-text) run locally, and the vector search index lives in the same database file (sqlite-vec).

**Three layers:**

- **Renderer** (`src/`) — React 19 + Tailwind v4 + Vite. **HashRouter** (`#/path`), React Context for state (`AuthContext`, `ColorThemeContext`, `ToastContext`). The renderer **never imports Node APIs directly** — every backend call goes through an `src/api/*Service.tsx` wrapper that delegates to `window.electron.ipcRenderer.invoke("<channel>", ...args)`. The bridge is fully typed in `src/electron.d.ts`; it used to be deliberately loose and incomplete, which is what most of the old renderer typecheck errors came from.
- **Main process** (`electron/`) — Node ESM (`"type": "module"`; reconstruct `__dirname` via `fileURLToPath(import.meta.url)`). `preload.js` exposes the bridge (emitted as CommonJS `preload.cjs`, because the windows are sandboxed and a sandboxed preload cannot be an ES module; `splashPreload.js` is the splash's own, smaller bridge); `ipcHandlers.js` routes each channel to a handler in `methods/*.js` (business logic), which reads/writes through `db/*.js` (SQLite; `connection.js` holds all DDL). `services/` holds the process managers and background services — `indexer.js` (the search indexer), `OllamaSetup.js`, `appSetup.js`, `autoUpdater.js`.
- **Optional online-sync backend** (`src/server/`) — Express 5 + PostgreSQL + S3 + JWT. **Unreachable**: the import is commented out at [electron/main.js:8](electron/main.js#L8). [docs/ONLINE_MODE_REMOVAL.md](docs/ONLINE_MODE_REMOVAL.md) judges it safe to delete. Don't build on it.

**Request flow:** UI component → `src/api/xService.tsx` → IPC channel → [electron/ipcHandlers.js](electron/ipcHandlers.js) → `electron/methods/x.js` → `electron/db/x.js` → SQLite.

**Background AI is event-driven.** Journal handlers emit on the `eventBus` ([electron/eventBus.js](electron/eventBus.js)); [electron/events.js](electron/events.js) forwards `journal:aiStarted` / `journal:aiCompleted` to the renderer via `webContents.send`, while the main process does the enrichment — title/tags/mood/summary generation through Ollama, and the search indexer (below) for embeddings. **AI metadata is never ready synchronously after a journal create/update.**

**Startup ordering matters** ([electron/main.js](electron/main.js), inside `app.whenReady()`): splash → `initDatabase()` → Ollama embedding-model setup → every IPC handler and the event bus register, synchronously (`startServices`, [electron/services/startServices.js](electron/services/startServices.js)) → the hidden main window is created → `services-ready` is sent with `{ degraded, search }`, and the window is shown once the renderer has painted. The search index needs no process to start (see **The search index** below): `startIndex` only checks that the sqlite-vec extension loaded and `onIndexReady` starts the indexer. **Handlers must exist before the window does, and nothing in the app may depend on search being available:** if the extension could not load, search and Ask return an `index-unavailable` result and everything else carries on. Do not put an `await` between `initDatabase()` and `createWindow()`; `scripts/bench/bench-startup.mjs` fails on any `No handler registered`.

## Conventions and gotchas

- **Renderer imports omit the file extension** (`import App from "./App"`). `allowImportingTsExtensions` is on, so both forms resolve, and 5 stray imports under `src/` do carry an explicit `.ts`/`.tsx`. The other 248 do not. This file used to document those 5 as the convention; it was describing the minority. Match the 248.
- **Schema changes go in [electron/db/migrations.js](electron/db/migrations.js)**, as a new entry appended to the ordered `MIGRATIONS` list. `runMigrations` applies everything newer than `PRAGMA user_version`, each migration in its own transaction together with its version stamp, and `initDatabase()` takes a `VACUUM INTO` snapshot into `<userData>/backups/` (5 kept) before the first one runs. **Never edit a shipped migration** — versions 1 to 3 are the pre-versioning schema and are idempotent only because they had to be; from 4 onward a migration runs exactly once per install, so it may be destructive. `migrations.js` is deliberately import-free (no `better-sqlite3`, no `electron`) so `runMigrations` is unit-testable; `connection.js` opens the DB as a module-level side effect and cannot be imported under vitest. The DB is still the user's only copy of their journal (`<userData>/mind-sage.db`, i.e. `%APPDATA%/MindSage/mind-sage.db` on Windows; an existing journal at the old macOS/Linux path is kept in place), so treat schema edits as high-risk. `MS_SKIP_DB_BACKUP=1` skips the snapshot.
- **Everything under `electron/` is bundled into `main.js`.** There are no worker threads and no `viteStaticCopy` targets any more (they existed only for `qdrantWorker.js`, which was spawned from a file path); a new main-process file needs no build config. A native dependency that must be loaded from disk (sqlite-vec's `vec0` library) is kept external by `vite.config.ts` (every `dependencies` entry is) and unpacked from the asar by `asarUnpack` in `package.json`; `electron/db/vectorExtension.js` rewrites `app.asar` to `app.asar.unpacked` when it resolves the path.
- **Import and export formats live in [electron/portability/](electron/portability/)**, one pure module per format (`detect`, `read`, `write` over a map of path to bytes, no `electron` or database imports) so each is unit-tested in `portability.test.js`. Add a format there, register it in `index.js` (readers are tried most specific first), and give it a round-trip test. Imports go through `electron/methods/portability.js`, which writes with `localDB.createJournalEntry` rather than the editor's create handler on purpose: the handler emits `journal:created`, which would queue AI title, tag and summary generation for every imported entry and overwrite the source's own. One `journal:bulk-sync-requested` afterwards indexes them for search. App logos come from Simple Icons via [AppLogo.tsx](src/components/settings/AppLogo.tsx); apps it does not carry get a lettered tile, not a logo copied from their site.
- **The main window has a Content-Security-Policy, and it stops the renderer loading anything from outside the app.** It covers subresource loads only: navigation and new windows (KAN-62) and the main process (updater, model and installer downloads) are separate controls, so do not describe it as proof that MindSage makes no outside requests. It is built in [electron/csp.js](electron/csp.js) and injected into `index.html` by a Vite plugin (strict for a build; the dev server also gets its hot-reload socket, and the React preamble). The renderer may load script, style, fonts and `connect-src` from the app's own files only (on a `file://` page `'self'` is not tighter than that), and images, audio and the PDF frame from `data:` and `blob:`. **If a screen needs something else, change the policy deliberately in `csp.js` and its test; do not loosen it to make an error go away.** No `fetch` to a URL, no remote image, no Google Fonts link, no inline `<script>`. The splash has its own policy in `public/splash.html`. **Every window is sandboxed, with context isolation and no Node** (main, Quick Capture and the splash), so a preload may import only `electron` and a page script can never `require`; a window that needs something from the main process gets a channel in the preload, not Node. [electron/windowGuard.js](electron/windowGuard.js) refuses new windows and any main-frame navigation or redirect away from the app's own pages (web and mail links go to the default browser; subframes are left to the CSP's `frame-src data:`; there is no permission-request handler yet), and `open-external` only takes `http:`, `https:` and `mailto:`. A `<meta>` policy cannot carry `frame-ancestors`, `report-uri` or `sandbox`.
- **The Windows uninstaller keeps the journal unless asked.** [assets/installer.nsh](assets/installer.nsh) (electron-builder's `buildResources` is `assets/`, so that is where it looks) adds a `customUnInstall` prompt, default No, that names the current user's `%APPDATA%\MindSage` (an all-users install is switched to the user context first). It never prompts or deletes during an update (`${isUpdated}`) or a silent uninstall, and leaves the `--delete-app-data` flag to electron-builder. There is no MSIX/appx target; if one is added, the Store removes the package's app data itself and this prompt does not apply. NSIS cannot be run off Windows; `installer.test.js` pins the properties and compiles it with `makensis` when present.
- **Updates are quiet and opt-in.** `electron/services/autoUpdater.js` checks only when the user turned on automatic checks or pressed "Check now"; `updateRelay.js` remembers where the download stands (`update:get-state`) and `UpdateBar` shows it. "Restart to update" goes through `prepareToRestart()` in [src/utils/unsavedWork.ts](src/utils/unsavedWork.ts): a screen holding text a restart would lose registers a guard there (the entry form does), and the restart is refused while one is dirty. Notices that sit above the page (`UpdateBar`, `AIReadinessBanner`) go in the wrapper in `App.tsx`, because the title bar is `fixed` over the top 40px.
- **Deleting is two steps: the trash, then a purge (KAN-52).** `journal:delete` and `goal:delete` only mark the row (`is_deleted = 1`, `deleted_at`); nothing is removed for 30 days. **Every query that reads entries or goals must filter `is_deleted = 0`**, including anything new (a new query that forgets it shows trashed items in search, Ask, counts or exports). Search results are built by joining the vector hits back to the base tables (`db/searchIndex.js` `searchSimilar`), which filter `is_deleted = 0`, so a trashed item cannot be returned even though its vector stays until the purge; the indexer's `storeVector` re-checks the item in the same transaction that writes its vector. [electron/db/trash.js](electron/db/trash.js) lists, restores and removes (`deleteForever` only ever touches rows already in the trash, and only the signed-in user's); [electron/methods/trash.js](electron/methods/trash.js) deletes the entry's whole `media/journals/<id>/` folder (photos, the original recording and its WAV) and every cached thumbnail of its photos (thumbnail names start with a hash of the photo's path, so all widths are found from the path), all confined to `userData/media` by [mediaPaths.js](electron/mediaPaths.js), runs the purge shortly after launch and every 24 h, and reports progress. The purge removes the item's vector and `search_index` row in the same transaction as the row itself (`removeSources`), so nothing is queued and nothing of the text is left in the index. Goals keep their progress logs while trashed. Saved Ask answers that cited a purged entry lose its quoted words (`redactQuotes.js` replaces every run of five or more words shared with the entry by "[entry removed]"). Backups made before a purge still contain the item, and the UI and Settings say so. Known limits of the answer scrub (KAN-53 review): it matches runs of five or more words against the entry's *current* text and its title (short entries only as a whole), so a sentence edited out of an entry before the purge can survive in an older answer; scripts written without spaces (Japanese, Chinese, Thai) are caught only as whole clauses; user messages are not scrubbed; `secure_delete` is on so removed rows are overwritten in the database file, and the purge truncates the WAL, and vectors are removed in the same transaction (the vector table's freed pages are overwritten the same way, unverified for vec0's chunk files).
- **Support lines are bundled data, and safety-critical** (KAN-50/54/55). [src/data/supportLines.ts](src/data/supportLines.ts) lists the lines per region (India, US, UK, Canada, Australia, Germany) with the date they were last checked; change a number only after checking the operator's own page and bump `VERIFIED_ON`. The first check (2026-10-19) was by web search of public pages, not against each operator's site, so a person re-checking them is still owed. `SupportSheet` works offline: a desktop cannot dial, so it shows the number, a copy button (with a select-the-number fallback when the clipboard is blocked) and a QR code (`tel:`/`sms:`) drawn locally with `qrcode-generator`, always on a white quiet zone, opened inside the card of the line it belongs to; under-18 lines are one compact row each, and "Other countries" lists the regions. iCall's hours differ between sources, so its note says to check their site. Voice-only lines never get a Text row. The region comes from the person's choice (`localStorage.support_region`) or the system language. The pinned link on Today (`PinnedSupportLink`) sits above the dock. Ask shows `ASK_DISCLAIMER` under the composer and in onboarding, and both Ask prompts carry `NO_ADVICE_RULE`.
- **The search index is sqlite-vec in the journal database (KAN-192, KAN-88).** `vec_entries` is a `vec0` virtual table (768-dimension float32, cosine distance, `user_id` partition key) created by `initDatabase()` through [electron/db/vectorExtension.js](electron/db/vectorExtension.js), not by a numbered migration, so a machine that cannot load the extension still opens its journal (`vectorSupport`, search then reports `index-unavailable`). `search_index` (migration 7) holds one state row per entry, goal and progress log: `state` pending / ok / failed, `attempts`, `next_attempt_at`, `content_hash`; its `id` is the vector's rowid. [electron/db/searchIndex.js](electron/db/searchIndex.js) is the data layer (everything that touches vectors goes through it: bind ids as `BigInt`, JS numbers bind as floats and fail the partition-key check). [electron/services/indexer.js](electron/services/indexer.js) runs in the main process (embedding is an HTTP call; there is no worker thread): the `journal:created/updated`, `goal:created/updated` and `progress_log:created` events (and `search:sync`, portability import, startup) mark items stale, and one loop embeds them in batches of 25 with a pause, yielding for 1.5 s after any write, backing off 1 min, 5 min, 30 min, 2 h, 12 h on a failure and giving up after 5 attempts until the text changes. Ollama being down is not a failure and spends no attempts. An edit that does not change the embedded text (mood, tags, a goal's progress) costs no embedding (`content_hash`). A model swap is `resetAll(dim)` plus the same loop. **New handlers that create or edit entries, goals or progress logs must emit the matching event with the row's `id`**; the renderer no longer asks for a sync. Progress reaches the renderer as `ai-status-event` `index:bulkStarted/Progress/Completed` and the per-entry `journal:indexStarted/Completed/Failed`. IPC is `search:query`, `search:sync`, `search:bulk-sync`, `search:status`. Journal lists carry `index_state` (ok / pending / failed / null) computed from `search_index`. Install upgrades drop the old Qdrant bookkeeping in migration 8 and delete `<userData>/qdrant-data` ([electron/legacyQdrant.js](electron/legacyQdrant.js)); nothing from Qdrant is needed because every vector is made again from the journal text. Measured on a 4-core sandbox (brute-force scan): 2 ms at 150 vectors, 12 ms at 5,000, 95-98 ms p50 and 109-113 ms p95 at 50,000 (int8 quantisation measured 73 ms p50 and was not adopted: recall unmeasured). 
- **Logging goes through [electron/log.js](electron/log.js) (KAN-170).** Import `{ log }` and call `log.debug/info/warn/error`; do not use `console` in the main process (`electron/noConsole.test.js` fails on it, with a short allowlist that must only shrink). The logger writes `userData/logs/mindsage.log`, rotating at 1 MB across 5 files, keeps the last 500 lines in memory if the folder cannot be written, rate-limits a chatty message, and only keeps `debug` when `MS_DEBUG=1`. [electron/logSetup.js](electron/logSetup.js) (imported second in `main.js`) also routes any leftover `console.*` into it. **Redaction ([electron/logRedact.js](electron/logRedact.js)) is a safety net, not permission to log writing:** it removes values under keys such as `content`, `title`, `prompt`, `summary`, `mood_tags`, drops media and journal paths and shortens long strings, but a short free-text string passed on its own cannot be recognised. So log ids, counts and lengths, never entry or chat text. The renderer's `console.warn`/`console.error` and uncaught errors reach the same file through the single `log:renderer` channel (`src/utils/rendererLog.ts`). The e2e run checks that no log file contains the entry it wrote. 
- **Native binaries live in `resources/`** (Whisper.cpp + DLLs, FFmpeg) and ship via `electron-builder` `extraResources`. Path resolution differs between dev (`../resources/...`) and packaged (`process.resourcesPath`) — copy the pattern in [electron/methods/whisper.js](electron/methods/whisper.js).
- **Env flags:** `MS_DISABLE_GPU=1` (Windows) disables GPU for machines with broken drivers ([main.js:124](electron/main.js#L124)); `MS_REMOTE_DEBUG=<port>` opens a loopback CDP endpoint ([main.js:137](electron/main.js#L137)) — anything that reaches it has full control of the renderer, so leave it off by default. `MS_USER_DATA_DIR=<dir>` points Electron's `userData` (the database, logs, media, electron-store files) at another directory, and a profile chosen this way always gets its own database; the benchmark harness also sets `APPDATA`, which the db-only bench scripts still resolve the database from, since they run without an Electron `app`. It is applied by [electron/userDataOverride.js](electron/userDataOverride.js), which must stay the first import in `main.js`.
- **Deleting a profile is one main-process transaction plus file cleanup** (KAN-56). `user:delete-summary` tells the screen what goes (counts, photo/recording bytes, other profiles); `user:delete-account` re-checks the password in the main process through `electron/attemptLimiter.js` (5 wrong tries lock it for 60 s, and a locked profile refuses even the right password), then `db/profile.js` `deleteProfile` removes the user row (cascade), queues vector deletions and returns the media to remove; `methods/profileDelete.js` removes files and thumbnails and drains the queue. Database backups are whole-DB snapshots shared by every profile: they are removed when the deleted profile was the last one, and otherwise replaced (`replaceBackups()` in `connection.js` takes a fresh snapshot after the rows are gone, then deletes the older ones) so no copy of the deleted journal survives. Files another program holds open (EBUSY on Windows) are written to `userData/pending-file-deletions.json` by `electron/pendingDeletions.js` and retried at every start and every purge; the empty `media/chats/<message>/<chat>/` folders are pruned after their attachments go (KAN-344). The renderer side is a Delete profile card on Settings, Profile (`DeleteProfileCard`: a backup offer via the export, a failed backup blocks deleting until it works or is skipped) that opens `DeleteProfileDialog` (what goes, what stays, password, `HoldButton`), and `utils/clearLocalTraces.ts` clears `userInfo` afterwards. The dialog is mounted once in `App.tsx`, outside the routes and driven by `utils/deleteProfileDialog.ts`, so its "deleted" screen survives the sign-out that deleting causes; nothing is deleted until the hold completes. Password checks (delete and change-password share one count) run one at a time per profile and the session ends the moment the rows are gone. The offered backup holds journal entries and their media only, not goals, chats or Trash, and the card says so. Drafts are cleared only with the last profile (draft keys are not per profile).
- **The session lives in the main process; there are no tokens.** [electron/session.js](electron/session.js) holds who is signed in, and every handler under `electron/methods/` reads it with `currentUserId()` (guarded, so signed-out calls refuse) rather than taking a credential from the renderer. **IPC channels take no `token` argument**: when you add one, read the user from the session, and never accept a user id from the renderer. Sign-in is `auth:login` (with `rememberMe`, persisted in electron-store `session.json`); `auth:get-session`, `auth:list-profiles` (the signed-out profile picker at `#/profiles`: id, username, full name and an avatar thumbnail, never email), `auth:logout` and the one-shot `auth:adopt-legacy-session` (upgrade path for old localStorage JWTs) are registered early with the setup IPC. Both windows follow the `auth:changed` broadcast. The password picks the account and keeps people out of the app; **it does not encrypt anything** (decision: option B), and the UI says so. Do not add copy that implies otherwise until encryption exists (a Jira ticket). `localStorage.userInfo` is a display cache only; never put anything in it a handler would trust.
