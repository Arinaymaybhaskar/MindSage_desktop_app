## Commands

```bash
npm run dev            # Vite dev server + Electron (vite-plugin-electron sets VITE_DEV_SERVER_URL). Normal way to run the app.
npm run build          # vite build && electron-builder → installers in release/
npm run release        # same, with --publish always (used by .github/workflows/release.yml on v* tags)
npm run rebuild        # electron-rebuild -f -w better-sqlite3
npm run postinstall    # runs rebuild automatically; without it better-sqlite3 fails to load at runtime
npm test               # vitest run (pure modules + renderer; needs no native build)
npm run test:db        # *.db.test.js under Electron-as-Node: real SQLite migrations, journal CRUD, backup, the AI worker thread
npm run test:e2e       # builds, then launches the real app (Playwright): sign up, write, wait for AI, search. Needs Ollama + Qdrant; E2E_SKIP_AI=1 skips those steps
npm run test:watch     # vitest
npm run typecheck      # tsc -p tsconfig.app.json --noEmit  (renderer only)
npm run lint           # eslint .
npm run format         # prettier --write .    (format:check for CI-style verification)
npm run bench          # SQLite/media/size benchmark suite → docs/benchmarks/results/
npm run bench:ipc      # IPC-boundary benchmark; needs the running app
npm run bench:quick    # db stage, ~25s; the pre-commit hook runs it when runtime code is staged
npm run bench:phase -- <n>   # full suite after MASTER_TODO phase n; needs Ollama, builds first
```

**Benchmarks come in two kinds, kept apart everywhere** (file location, `kind` field, website): a **quick** run on every commit that stages runtime code, from the pre-commit hook, never committed and never blocking; and a **full** run at the end of every MASTER_TODO phase, committed. Finishing a phase is not done until `npm run bench:phase -- <n>` has run and its results are committed with a run-index row. See [docs/benchmarks/README.md](docs/benchmarks/README.md#two-kinds-of-run).

Targeted runs: `npm run bench -- --label after-<change>` then `npm run bench -- --compare baseline --label after-<change>`. [docs/benchmarks/BASELINE.md](docs/benchmarks/BASELINE.md) is **generated — never hand-edit it**; [FINDINGS.md](docs/benchmarks/FINDINGS.md) is the hand-written reading, and it **corrects PERFORMANCE.md in two places**. Trust the measurements over the audit prose.

**Running a subset of tests:**

```bash
npx vitest run src/utils/DateFormatter.test.ts   # one file
npx vitest run -t "formats a relative date"       # one test by name
```

**Typecheck, lint and format are all clean; keep them that way.** As of 2026-08-28 `npm run typecheck`, `npm run lint` and `npm run format:check` all report **zero** problems, and tests are green (5 files, 35 tests). This replaces a long-standing baseline of 131 typecheck errors and 106 lint problems, cleared wholesale in a single pass. **A non-zero typecheck or lint exit now means you broke something**, so treat it as a real failure rather than comparing counts against a tolerated baseline.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) **blocks on all four**: typecheck, lint, `format:check` and `npm test`. The `continue-on-error: true` that made the first two report-only is gone, so a red `Typecheck & Lint` check now means what its name says. The pre-commit hook catches the same problems earlier (see **Other tooling** below), but it can be bypassed with `--no-verify`; CI cannot.

Three things that clean-up established, so treat them as conventions rather than incidental style:

- **The IPC bridge is typed, not `any`.** [src/electron.d.ts](src/electron.d.ts) now describes the whole `preload.js` surface, and `window.electron.ipcRenderer.invoke` is generic with an `unknown` default. Callers state the shape they expect, usually through the declared return type of the `src/api/*Service` wrapper that owns the channel. When you add a channel, type its wrapper against what the handler in `electron/methods/*` actually returns; when you add a member to the bridge, add it here too.
- **Context hooks live in `src/hooks/`, not beside the provider.** `useAuth`, `useToast` and `useColorThemeContext` each sit in their own file so the context modules export only components, which is what React Fast Refresh needs and what `react-refresh/only-export-components` enforces. Adding a hook back into a `src/context/*.tsx` file will fail lint.
- **Row shapes live in `src/types/`.** `User.ts`, `Goals.ts`, `Dashboard.ts`, `Ollama.ts`, `Qdrant.ts` and `sqlite.ts` mirror the DDL in [electron/db/connection.js](electron/db/connection.js). SQLite has no boolean, so 0/1 columns are typed `SqliteBoolean`; prefer extending these over redeclaring a near-copy in a component.

**Database tests are a second project.** better-sqlite3 is built for Electron's ABI, so anything that touches the real database is a `*.db.test.js` file, excluded from `npm test` and run by `npm run test:db` under `ELECTRON_RUN_AS_NODE=1` ([vitest.db.config.ts](vitest.db.config.ts), [scripts/run-db-tests.mjs](scripts/run-db-tests.mjs); it needs the `electron-rebuild` build from `postinstall`). They use `electron/db/dbTestUtils.js` and choose their folder through `MS_DB_DIR` / `MS_USER_DATA_DIR` before the first import, because `connection.js` opens the database as a side effect. `qdrantWorker.db.test.js` runs the real worker thread against fake Ollama (it must own port 11434, because the worker hard-codes it) and fake Qdrant servers. A new migration needs a case in `migrations.db.test.js`. The end-to-end run is `scripts/e2e/run.mjs`; it waits on the app's own events, never a sleep.

**Test conventions:** tests sit next to the module they cover (`electron/methods/jsonStream.test.js`, `src/api/journalService.test.ts`). [vitest.config.ts](vitest.config.ts) is deliberately separate from [vite.config.ts](vite.config.ts) so `vite-plugin-electron` doesn't boot during tests; it uses jsdom, `globals: true`, `src/test/setup.ts`, and `pool: "threads"` (the default `forks` pool hangs on newer Node). `electron/**` is in the include list, but only **pure modules** are testable there — anything importing `better-sqlite3` or `electron` won't load. `electron/methods/` is no longer copied into the package at all, so the explicit test exclusion that used to sit in the `viteStaticCopy` targets is gone with it.

**Other tooling:** husky's [pre-commit hook](.husky/pre-commit) does two things. First `gitleaks protect --staged` (warns and passes through if gitleaks isn't installed — install it for real protection; allowlist false positives in `.gitleaks.toml`). Then `lint-staged`, which runs `prettier --write` on staged files and `eslint --fix --max-warnings=0` on staged `.ts`/`.tsx`, re-staging whatever it fixes. A commit that would introduce a lint error or a warning is refused. ESLint's flat config ([eslint.config.js](eslint.config.js)) matches only `**/*.{ts,tsx}`, which is why the `lint-staged` globs in `package.json` send `.js`/`.mjs` to Prettier alone; adding them to the ESLint glob makes it fail with "no matching configuration". **That means the whole main process is formatted but never linted** — `electron/**` and `scripts/**` are plain `.js`/`.mjs`, so `npm run lint` says nothing about them. Widening the config is a real (unclaimed) improvement, not a one-line glob change: those files would report fresh errors on their first run. Prettier (`.prettierrc`: LF, double quotes, semicolons, trailing commas, 80 columns) was applied across the repo in one sweep after years of drift, so `format:check` passes; `.prettierignore` excludes all `*.md`, which is why this file is exempt, and also skips `public/rive/` (a vendored webpack bundle) and `docs/benchmarks/results/` (regenerated by every `npm run bench`). [.gitattributes](.gitattributes) pins the working tree to LF on every platform, without which `format:check` would pass on the Linux runner and fail on a fresh Windows clone. `.npmrc` sets `engine-strict=true` against the Node 20–24 range in `package.json`; `.nvmrc` pins 20.

## Branching and workflow

`main` is protected on GitHub: no direct pushes (enforced for admins too), no force-pushes, no deletions, and merging requires the `Typecheck & Lint` check to pass, which now genuinely means typecheck, lint **and** `npm test` all passing (see above). All work happens on a branch off `main` and lands via PR.

### Naming: branches, commits and pull requests

Work is tracked in Jira, project **KAN** (MindSage) at arinaymaybhaskar7500.atlassian.net. Every branch, commit and PR that does a ticket names its key, so the work and the ticket find each other. One ticket per branch and per PR.

**Branches:** `<type>/<KEY>-<slug>`, for example `fix/KAN-58-ipc-survives-qdrant` or `feat/KAN-52-trash`.

- `<type>` is the conventional-commit type of the main change: `feat` (user-visible behaviour), `fix` (a bug), `perf`, `refactor`, `test`, `build` (packaging, electron-builder, Vite), `ci`, `chore`, `docs`.
- `<KEY>` is the Jira key in capitals. Work with no ticket drops it: `docs/naming-conventions`. Anything bigger than a typo should get a ticket first.
- `<slug>` is two to five lowercase words joined by hyphens, from the ticket summary.
- Delete both the local and remote branch immediately after merge; don't let merged branches accumulate.
- `phase/p<n>-<slug>` — one per roadmap phase (the Jira release), for example `phase/p1-make-the-promise-true`, cut from `main` when the phase starts. Ticket branches for that phase branch from it and merge back into it, never straight into `main`. When the phase's gate passes and `npm run bench:phase -- <n>` is committed, the phase branch lands in `main` through one PR. Merge `main` into an open phase branch (never rebase it) whenever `main` moves. CI runs on every pull request whatever its base, but not on direct pushes to a phase branch, so run typecheck, lint, `format:check` and `npm test` before merging into one by hand.
- `backup/<slug>` — a snapshot taken before a history rewrite or other destructive git operation (e.g. `backup/pre-coauthor-removal`, taken before stripping `Co-Authored-By` trailers from history). Kept indefinitely as cheap insurance.
- `archive/<slug>` — work deliberately abandoned but kept for reference (e.g. `archive/redesign-preview`, a scrapped redesign). Not meant to merge.
- `claude/<slug>` — branches Claude Code creates on its own in cloud sessions. Rename to the pattern above before opening a PR for ticket work.

**Bugs found along the way:** when ticket work, a review or a benchmark turns up a bug that is not the ticket's own, do not widen the ticket. File a Jira **Bug** in project KAN under the closest epic, labelled `found-in-phase-<n>` and `phase-<n>-closeout`, with the phase's release as its fix version, a description saying where it was found and whether it was reproduced or only read from the code, and acceptance criteria. Say so in the PR. Closing a phase includes fixing everything labelled `phase-<n>-closeout` (or deliberately moving it to a later release) before the phase branch goes to `main`.

**Commits:** [Conventional Commits](https://www.conventionalcommits.org/), as the history already uses: `type(scope): summary`.

- `scope` is the area touched, matching the existing history: `startup`, `db`, `auth`, `journal`, `goals`, `search`, `ai`, `chat`, `people`, `media`, `portability`, `settings`, `updater`, `ui`, `bench`. Leave it out when a change spans the app.
- The summary is imperative, lower case, no full stop, under about 72 characters: `fix(startup): keep IPC working when Qdrant fails to start`.
- The body says why, and what was checked. The last line before any trailers is `Refs: KAN-58`; the Jira GitHub integration links commits by that key.
- A breaking change to stored data or IPC gets `!` after the scope (`feat(db)!: …`) and a `BREAKING CHANGE:` line saying what an existing install goes through.

**Pull requests:** a ticket PR targets its phase branch, not `main`. Title `KAN-58: <ticket summary>`, for example `KAN-58: IPC survives a Qdrant failure`. The body links the ticket, copies its acceptance criteria as a checklist ticked against what was verified, and lists anything left for a follow-up ticket. A ticket labelled `opus-review` in Jira (journal data, migrations, security, the AI pipeline) is reviewed with Opus before merge.

## Architecture

Electron + React + TypeScript desktop journaling app, **offline-first**: data lives in a local `better-sqlite3` DB, and Ollama (generation/embeddings), Qdrant (vector search), and Whisper.cpp (speech-to-text) all run locally.

**Three layers:**

- **Renderer** (`src/`) — React 19 + Tailwind v4 + Vite. **HashRouter** (`#/path`), React Context for state (`AuthContext`, `ColorThemeContext`, `ToastContext`). The renderer **never imports Node APIs directly** — every backend call goes through an `src/api/*Service.tsx` wrapper that delegates to `window.electron.ipcRenderer.invoke("<channel>", ...args)`. The bridge is fully typed in `src/electron.d.ts`; it used to be deliberately loose and incomplete, which is what most of the old renderer typecheck errors came from.
- **Main process** (`electron/`) — Node ESM (`"type": "module"`; reconstruct `__dirname` via `fileURLToPath(import.meta.url)`). `preload.js` exposes the bridge (emitted as CommonJS `preload.cjs`, because the windows are sandboxed and a sandboxed preload cannot be an ES module; `splashPreload.js` is the splash's own, smaller bridge); `ipcHandlers.js` routes each channel to a handler in `methods/*.js` (business logic), which reads/writes through `db/*.js` (SQLite; `connection.js` holds all DDL). `services/` holds the process managers — `qdrantManager.js`, `OllamaSetup.js`, `appSetup.js`, `autoUpdater.js`.
- **Optional online-sync backend** (`src/server/`) — Express 5 + PostgreSQL + S3 + JWT. **Unreachable**: the import is commented out at [electron/main.js:8](electron/main.js#L8). [docs/ONLINE_MODE_REMOVAL.md](docs/ONLINE_MODE_REMOVAL.md) judges it safe to delete. Don't build on it.

**Request flow:** UI component → `src/api/xService.tsx` → IPC channel → [electron/ipcHandlers.js](electron/ipcHandlers.js) → `electron/methods/x.js` → `electron/db/x.js` → SQLite.

**Background AI is event-driven.** Journal handlers emit on the `eventBus` ([electron/eventBus.js](electron/eventBus.js)); [electron/events.js](electron/events.js) forwards `journal:aiStarted` / `journal:aiCompleted` to the renderer via `webContents.send`, while the Qdrant worker (`qdrantWorker.js`, a `Worker` thread) does the enrichment — title/tags/mood/summary generation and embeddings. **AI metadata is never ready synchronously after a journal create/update.**

**Startup ordering matters** ([electron/main.js](electron/main.js), inside `app.whenReady()`): splash → `initDatabase()` → Ollama embedding-model setup → every IPC handler and the event bus register, synchronously (`startServices`, [electron/services/startServices.js](electron/services/startServices.js)) → `startQdrant()` runs in the background (spawns the Qdrant binary, picks a free port into `process.env.QDRANT_HTTP_PORT`, retried after 10, 30 and 60 s if it fails) → the hidden main window is created → `services-ready` is sent with `{ degraded, search }` once Qdrant has started or failed, and the window is shown once the renderer has painted. **Handlers must exist before the window does, and nothing in the app may depend on Qdrant being up:** search and Ask return an `index-unavailable` result while it is down, and `qdrant:*` handlers wait up to 20 s for the first start to end. Do not put an `await` between `initDatabase()` and `createWindow()`; `scripts/bench/bench-startup.mjs` fails on any `No handler registered`. If you touch Qdrant or embedding init, verify the worker still receives `QDRANT_HTTP_PORT`.

## Conventions and gotchas

- **Renderer imports omit the file extension** (`import App from "./App"`). `allowImportingTsExtensions` is on, so both forms resolve, and 5 stray imports under `src/` do carry an explicit `.ts`/`.tsx`. The other 248 do not. This file used to document those 5 as the convention; it was describing the minority. Match the 248.
- **Schema changes go in [electron/db/migrations.js](electron/db/migrations.js)**, as a new entry appended to the ordered `MIGRATIONS` list. `runMigrations` applies everything newer than `PRAGMA user_version`, each migration in its own transaction together with its version stamp, and `initDatabase()` takes a `VACUUM INTO` snapshot into `<userData>/backups/` (5 kept) before the first one runs. **Never edit a shipped migration** — versions 1 to 3 are the pre-versioning schema and are idempotent only because they had to be; from 4 onward a migration runs exactly once per install, so it may be destructive. `migrations.js` is deliberately import-free (no `better-sqlite3`, no `electron`) so `runMigrations` is unit-testable; `connection.js` opens the DB as a module-level side effect and cannot be imported under vitest. The DB is still the user's only copy of their journal (`<userData>/mind-sage.db`, i.e. `%APPDATA%/MindSage/mind-sage.db` on Windows; an existing journal at the old macOS/Linux path is kept in place), so treat schema edits as high-risk. `MS_SKIP_DB_BACKUP=1` skips the snapshot.
- **`viteStaticCopy` copies only what `qdrantWorker.js` needs at runtime**: the worker itself, `eventBus.js`, `db/connection.js`, and `db/migrations.js`. Everything else under `electron/` is bundled into `main.js`, so adding a file there needs no config change. The targets used to be `db/*`, `methods/*` and `services/*`, which shipped about 25 files as a second, dead copy of code already in the bundle. Only add a target if `qdrantWorker.js` gains an import: the worker is spawned from a file path rather than imported, so its dependencies have to exist as real files, and missing one breaks the packaged build while dev mode keeps working.
- **Import and export formats live in [electron/portability/](electron/portability/)**, one pure module per format (`detect`, `read`, `write` over a map of path to bytes, no `electron` or database imports) so each is unit-tested in `portability.test.js`. Add a format there, register it in `index.js` (readers are tried most specific first), and give it a round-trip test. Imports go through `electron/methods/portability.js`, which writes with `localDB.createJournalEntry` rather than the editor's create handler on purpose: the handler emits `journal:created`, which would queue AI title, tag and summary generation for every imported entry and overwrite the source's own. One `journal:bulk-sync-requested` afterwards indexes them for search. App logos come from Simple Icons via [AppLogo.tsx](src/components/settings/AppLogo.tsx); apps it does not carry get a lettered tile, not a logo copied from their site.
- **The main window has a Content-Security-Policy, and it stops the renderer loading anything from outside the app.** It covers subresource loads only: navigation and new windows (KAN-62) and the main process (updater, model and installer downloads) are separate controls, so do not describe it as proof that MindSage makes no outside requests. It is built in [electron/csp.js](electron/csp.js) and injected into `index.html` by a Vite plugin (strict for a build; the dev server also gets its hot-reload socket, the React preamble and the local Qdrant inspector). The renderer may load script, style, fonts and `connect-src` from the app's own files only (on a `file://` page `'self'` is not tighter than that), and images, audio and the PDF frame from `data:` and `blob:`. **If a screen needs something else, change the policy deliberately in `csp.js` and its test; do not loosen it to make an error go away.** No `fetch` to a URL, no remote image, no Google Fonts link, no inline `<script>`. The splash has its own policy in `public/splash.html`. **Every window is sandboxed, with context isolation and no Node** (main, Quick Capture and the splash), so a preload may import only `electron` and a page script can never `require`; a window that needs something from the main process gets a channel in the preload, not Node. [electron/windowGuard.js](electron/windowGuard.js) refuses new windows and any main-frame navigation or redirect away from the app's own pages (web and mail links go to the default browser; subframes are left to the CSP's `frame-src data:`; there is no permission-request handler yet), and `open-external` only takes `http:`, `https:` and `mailto:`. A `<meta>` policy cannot carry `frame-ancestors`, `report-uri` or `sandbox`.
- **The Windows uninstaller keeps the journal unless asked.** [assets/installer.nsh](assets/installer.nsh) (electron-builder's `buildResources` is `assets/`, so that is where it looks) adds a `customUnInstall` prompt, default No, that names the current user's `%APPDATA%\MindSage` (an all-users install is switched to the user context first). It never prompts or deletes during an update (`${isUpdated}`) or a silent uninstall, and leaves the `--delete-app-data` flag to electron-builder. There is no MSIX/appx target; if one is added, the Store removes the package's app data itself and this prompt does not apply. NSIS cannot be run off Windows; `installer.test.js` pins the properties and compiles it with `makensis` when present.
- **Updates are quiet and opt-in.** `electron/services/autoUpdater.js` checks only when the user turned on automatic checks or pressed "Check now"; `updateRelay.js` remembers where the download stands (`update:get-state`) and `UpdateBar` shows it. "Restart to update" goes through `prepareToRestart()` in [src/utils/unsavedWork.ts](src/utils/unsavedWork.ts): a screen holding text a restart would lose registers a guard there (the entry form does), and the restart is refused while one is dirty. Notices that sit above the page (`UpdateBar`, `AIReadinessBanner`) go in the wrapper in `App.tsx`, because the title bar is `fixed` over the top 40px.
- **Deleting is two steps: the trash, then a purge (KAN-52).** `journal:delete` and `goal:delete` only mark the row (`is_deleted = 1`, `deleted_at`); nothing is removed for 30 days. **Every query that reads entries or goals must filter `is_deleted = 0`**, including anything new (a new query that forgets it shows trashed items in search, Ask, counts or exports). Search results come from Qdrant, which knows nothing about the trash, so `SemanticSearch` passes them through `localDB.filterLiveResults`; the worker re-checks `is_deleted` before it indexes. [electron/db/trash.js](electron/db/trash.js) lists, restores and removes (`deleteForever` only ever touches rows already in the trash, and only the signed-in user's); [electron/methods/trash.js](electron/methods/trash.js) deletes the entry's whole `media/journals/<id>/` folder (photos, the original recording and its WAV) and every cached thumbnail of its photos (thumbnail names start with a hash of the photo's path, so all widths are found from the path), all confined to `userData/media` by [mediaPaths.js](electron/mediaPaths.js), runs the purge shortly after launch and every 24 h, and reports progress. Removing a row queues its search-index points in `vector_deletions`, and `processVectorDeletions()` finishes the queue whenever the index is up, so a purge while Qdrant is down is completed later instead of leaving text behind. Goals keep their progress logs while trashed. Saved Ask answers that cited a purged entry lose its quoted words (`redactQuotes.js` replaces every run of five or more words shared with the entry by "[entry removed]"). Backups made before a purge still contain the item, and the UI and Settings say so.
- **Native binaries live in `resources/`** (Qdrant, Whisper.cpp + DLLs, FFmpeg) and ship via `electron-builder` `extraResources`. Path resolution differs between dev (`../resources/...`) and packaged (`process.resourcesPath`) — copy the pattern in [electron/methods/whisper.js](electron/methods/whisper.js).
- **Env flags:** `MS_DISABLE_GPU=1` (Windows) disables GPU for machines with broken drivers ([main.js:124](electron/main.js#L124)); `MS_REMOTE_DEBUG=<port>` opens a loopback CDP endpoint ([main.js:137](electron/main.js#L137)) — anything that reaches it has full control of the renderer, so leave it off by default. `MS_USER_DATA_DIR=<dir>` points Electron's `userData` (the database, logs, media, `qdrant-data`, electron-store files) at another directory, and a profile chosen this way always gets its own database; the benchmark harness also sets `APPDATA`, which the db-only bench scripts still resolve the database from, since they run without an Electron `app`. It is applied by [electron/userDataOverride.js](electron/userDataOverride.js), which must stay the first import in `main.js`.
- **The session lives in the main process; there are no tokens.** [electron/session.js](electron/session.js) holds who is signed in, and every handler under `electron/methods/` reads it with `currentUserId()` (guarded, so signed-out calls refuse) rather than taking a credential from the renderer. **IPC channels take no `token` argument**: when you add one, read the user from the session, and never accept a user id from the renderer. Sign-in is `auth:login` (with `rememberMe`, persisted in electron-store `session.json`); `auth:get-session`, `auth:list-profiles` (the signed-out profile picker at `#/profiles`: id, username, full name and an avatar thumbnail, never email), `auth:logout` and the one-shot `auth:adopt-legacy-session` (upgrade path for old localStorage JWTs) are registered early with the setup IPC. Both windows follow the `auth:changed` broadcast. The password picks the account and keeps people out of the app; **it does not encrypt anything** (MASTER_TODO 15, option B), and the UI says so. Don't add copy that implies otherwise until item 18 exists. `localStorage.userInfo` is a display cache only; never put anything in it a handler would trust.
